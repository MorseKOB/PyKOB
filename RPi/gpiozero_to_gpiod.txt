## Basic Output (Firing a Sounder or Loop)

## Precision Timing: Edge-Triggered Interrupts (Morse Decoding)
Because gpiod bypasses multiple layers of Python wrappers and queries the kernel queue instantly, it provides a much more precise timing capture loop for fast Morse parsing.

* gpiozero Pattern:

from gpiozero import Button

    print("Key pressed")

* gpiod Pattern:

settings = gpiod.LineSettings(
    direction=Direction.INPUT,
    bias=Bias.PULL_UP,
    edge_detection=Edge.BOTH  # Watch for both press and release events
)
with gpiod.request_lines("/dev/gpiochip0", config={18: settings}) as request:
    while True:
        # Wait indefinitely until an edge transition happens on the wire
        if request.wait_edge_events():
            for event in request.read_edge_events():
                # Grabs nanosecond precision timestamps directly from the kernel
                timestamp_ns = event.timestamp_ns
                print(f"Edge type: {event.event_type} at {timestamp_ns}")

## 1. The Hardcoded Device Mappings
On modern Linux kernels (like the one running on your Bookworm image), the physical 40-pin header lines are distributed across these specific /dev/gpiochipX device nodes: [1] 

| Model | gpiod Chip Device Path | Reason |
|---|---|---|
| Raspberry Pi 3 | /dev/gpiochip0 | Direct Broadcom SoC mapping |
| Raspberry Pi 4 | /dev/gpiochip0 | Direct Broadcom SoC mapping |
| Raspberry Pi 5 | /dev/gpiochip4 | Switched to the new dedicated RP1 Southbridge chip |

Note on Pi 5: On the absolute latest system kernel packages (apt upgrade), the kernel developers patched an alias rule to mirror the header onto /dev/gpiochip0 for backwards compatibility. However, hardcoding 4 as your fallback or scanning dynamically remains the safest production approach for older Pi 5 images. [2]

## 2. The Professional Solution: Dynamic System Enumeration
Rather than forcing your users to manually select their Raspberry Pi model inside your Configure.py app, you can use gpiod's built-in system scanner to detect the correct header chip dynamically on boot. [3] 
When gpiod scans the chips on a Raspberry Pi, the true 40-pin main header controller chip is always flagged with the label pinctrl or bcm2835. You can use this quick helper function in your code to automatically return the working chip path regardless of the Pi hardware generation it's running on: [4, 5] 

import os
def get_actual_gpio_chip():
    """
    Dynamically scans /dev/ for all available gpiochips and automatically
    returns the path of the chip driving the main 40-pin header.
    """
    for dev in sorted(os.listdir('/dev/')):
        if dev.startswith("gpiochip"):
            path = f"/dev/{dev}"
            try:
                # Open the chip layer to read its identifier label metadata
                import gpiod
                with gpiod.Chip(path) as chip:
                    info = chip.get_info()
                    # On Pi 3/4 this label is usually 'bcm2835-gpiomem' or similar
                    # On Pi 5 this label tracks the 'pinctrl' sub-architecture
                    if "pinctrl" in info.label or "bcm2" in info.label:
                        return path
            except Exception:
                continue
                
    # Bulletproof fallback architecture if discovery permissions are tight
    return "/dev/gpiochip0" 

By dropping a discovery routine like this into your core initialization layer, your Configure.py wrapper app can stay completely decoupled from hardcoded hardware assumptions. It can dynamically track whether the board is a 3, 4, or 5 seamlessly without complicating your storage configuration files!
